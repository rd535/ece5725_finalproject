PiPacer

A multi-mode LED pacing system
By Tyler Tisinger, Rhea Desai, and Andrew Lin
Last updated: 05/10/2026

Rainbow Lighting Mode

Demonstration Video

Introduction

The goal of this project is to develop a multi-use wavelight product designed for usage inside of Barton Hall. There are 3 main components: Pacer mode for track practices and races, Lighting mode for dynamic visual patterns, and Music mode which processes audio input to synchronize lightning with beats per minute (BPM) of a song. The project initially focused on creating a scalable pacer wavelight system suitable for a large indoor track meets, but the Music and Lighting modes were later incorporated to expand functionality and reflect team members’ interests in music integration. Thus, the goal of the project was not just to create an application that works in the lab and demo environment, but to make it robust enough to be deployed into the real world in a multipurpose track/event space such as Barton Hall. Significant effort went into designing and testing to ensure a seamless and intuitive user experience while maintaining high performance across all system features.

Project Overview

At a high level, the team utilized a Raspberry Pi 4 to host a web server that enables users to control an LED strip across three distinct modes: Pacer, Music, and Lighting. Through multiple development iterations, the project resulted in a fully functional and responsive web-based control system, with over 3,000 lines of code implemented to support backend logic, hardware interfacing, and frontend interaction. Additional features such as saved presets and event logging were integrated to enhance usability and provide persistent configuration and system feedback.

Design and Testing

Overall Architecture

To accomplish the project goals, a robust tech stack was developed to provide significant flexibility and scalability. The first design decision was choosing which software library to use for hosting a web server to allow a user to easily interface with the hardware. The team selected Flask since it is lightweight and easy to scale effectivly for a project of our size. Flask acts as a web framework that handles incoming HTTP requests, routes them to the appropriate backend logic, and returns responses to the user interface. Once the hosting framework was chosen, Python was used as the primary programming language because of the team’s familiarity and proficiency with it. The Python backend defines the application logic and API endpoints that Flask exposes for client interaction. The team then found a software library (rpi-ws281x) that could drive the LED strip and opted for a Python-based implementation to maintain consistency across the stack. For the front end, HTML and Javascript were chosen as they are easily supported by Flask and offer creative freedom with the front end. JavaScript communicates with the Flask backend by sending asynchronous requests via fetch to Python-defined routes, allowing real-time updates and control of the system without requiring full page reloads. This interaction enables seamless data exchange between the user interface and the hardware control logic.The tech stack is summarized in the figure below.

Methodology

The pacer stack is organized as a full, Flask-based control pipeline that evolved significantly throughout the development process. The design and test process that was utilized by the team was a Git workflow alongside frequent, isolated testing of individual features. A shared Github repository was established early on and used by the team to organize and share files between members, as well as streamlining deployment of the latest project version onto the Raspberry Pi for testing.

For most of the features that were important to the project and required a more thoughtful approach - such as the lighting manager, pattern classes, and the HTML and JS front end - isolated testing was done with test files that could validate each component independently. This was beneficial since it allowed the team to start with implementing the most basic features and understanding their interactions first, before then slowly expanding the implementation toward a full feature implementation.

Once this testing phase was complete, full process integration began. Git branching was used during this portion so that new features could be developed, while still maintaining a clean and working application on the main branch. Many of the features were incrementally added through this method. After a feature was implemented, it was pushed to the Github repository and then pulled onto the Pi for real world testing and user validation.

The main regret is not looking into a better pipeline for testing frontend features. The current workflow of having to sync repositories on the web and then the Pi, along with running the program, and then user debugging, slowed iteration speed. Having local frontend simulation or automated testing tools would have improved development efficiency, and would have increased the speed of the test pipeline

External Libraries

The rpi_ws281x library - licensed to the git user jgarff, but credit to all other contributors - was chosen to drive the LED strip since it was the most capable and flexible open source LED strip library. This library provides a reliable Python wrapper of the C library to generate the waveforms required to drive the wavelight strip. The strip is required to be driven at 800 kHz to meet its timing requirement, and this library ensures that the bit rate is precisely maintained, enabling correct color transmission while preventing flickering and data corruption. Not only does this library allow precise GPIO control for the data line to the strip, it also provided an API to allow easy control of specific LED indecies and brightnss. The GPIO method used to drive the LED strip was chosen to be PWM as it would offload the majority of the load to a Pi hardware peripheral and decrease CPU usage. This required the team to disable certain Linux features, such as onboard Pi audio, that could conflict with PWM usage.

Pacer Implementation Details

The pacer implemenation started with an isolated test directory with 3 simple files - manager, pattern, test. This provided a minimal framework to test the rpi_ws281x library along with exploring initial design ideas for how a pacer should behave. In this first approach, each pacer pattern owned its own LED strip object and independently controlled which LEDs were updated each cycle, as dictated by set pace speed. The manager was made to be a basic scheduler and would determine when each activ pacer object would run.

However, once most features were implemented and tested for both dynamic and constant pacer classes, the system was tested with multiple concurrent pacers, and a major architectural issue emerged. Allowing each pattern object to own its own LED strp instance caused conflicts at the hardware interface level and led to corrupted data signals and frozen strip behavior.

To resolve this, the architecture was redesigned around a centralized Pacer Manager, which is now the sole owner of the LED strip interface object. All pacer objects register with this manager, which collects positional data from each active pacer, resolves index conflicts (prioritizing faster pacers when overlap occurs), and performs a single strip update after all patterns have been iterated through. This updated approach ensures predictable behavior and eliminates race conditions that were apparent in the initial implementation.

Further up in the pacer stack is the front end portion, implemented through HTML and JavaScript. Since HTML and JS are unfamiliar for web app UI development along with their integration with Flask routes, a few hours were spent slowly creating and testing with an isolated test directory similar to the pacer manager and patterns.

After getting a baseline understanding of the process flow, the HTML-based user interface (pacer_v3.html) was iteratively created and provides a table-driven system for configuring pacers. Each row corresponds directly to a pacer object and allows the user to define parameters such as pace, lap count, color, and pacer type.


Over time, the UI evolved from a simple input form into a fully interactive system supporting multiple simultaneous pacers, preset management, LED strip configuration, and an integrated event log. To improve usability, constant pacers allow users to define a lap pace and total laps, while dynamic pacers expand the interface to accept per-lap pace inputs when additional laps are added.

The biggest challenge was maintaining a consistent UI look and feel across the entire application, which required incremental CSS, HTML, and JavaScript logic with each new feature addition. This also slowed down the development process, as forgetting to change any of the above layers would require revisiting the code, implementing the fix, and then rerunning the entire test pipeline for a simple frontend feature. However, investing the time to refine the frontend is critical for achieving a production-level product, as was the goal with this final project.

Now moving down a layer, the JavaScript that is integrated within the HTML handles all browser-side logic and acts as the translation layer between the UI and backend system. It dynamically updates the pacer table, loads saved presets, converts user inputs into structured JSON, and sends requests to backend endpoints using asynchronous fetch calls. It also continuously polls the backend through Flask routes to update pacer status, runtime information, and event logs, ensuring the UI reflects real-time system behavior.


On the backend, the Flask application (app.py) maintains system state using structured dictionary data structurs. pi_state["pacers"] stores user-defined configuration and UI state, while pacer_instances holds the active Python pacer objects. Flask routes update these structures when users modify pacers, start or stop execution, adjust LED settings, or load presets. The backend also manages mode switching (Pacer, Lighting, Music) to prevent multiple managers from attempting to control the LED strip simultaneously, as was found to be detrimental during the early pacer testing.

To improve flexibility and reach a production-level implementation, the system transitioned from hardcoded LED strip parameters (for our current 5m strip, 60 LED/m) to a shared JSON-based state model, allowing user-defined LED strip configurations to be saved and loaded across sessions. Pacer presets were also added to this data structure to improve usability by allowing the user to only have to define pacer configurations once and then reuse infinitely. The preset functionality was redesigned to eliminate the need for external file uploads, which had been initially considered in the project proposal. Instead, users can save and load configurations directly within the application, allowing them to save and load as many configured pacers they want and then easily load them in. Additionally, the system automatically reloads the most recent configuration on startup, further streamlining the user experience and reducing setup time.


The final major feature implemented is an integrated event logging system to improve debugging and user feedback. Events such as pacer creation, updates, errors, and mode transitions are recorded both in the UI and in a rolling log file capped at the 200 most recent entries to prevent excessive storage usage. This ensures that users can monitor system behavior in real time without relying on terminal output, making the system more robust for demonstrations and eventual real world deployment.


Several smaller, quality of life features were incrementally added to improve overall system interaction. One key improvement was overhauling the input table to have more intuitive and flexible user controls. For example, dynamic pacers allow users to set a different pace for each lap. Now, when the user chooses how many laps the dynamic pacer will make, the interface will automatically genreate input fields for each of the laps. This makes it clearer how data should be entered while reducing user error and hiding unnecessary fields.

Another important enhancement was the introduction of an “active pacer” table to only allow the user to control pacers that are actively loaded onto the Pi and currently controlled by the pacer manager. Rather than immediately treating all input table enterprise as active, the user must first send their configured pacers to the Raspberry Pi, at which point the system validates and registers them as active pacers. This is returned as feedback to the user through the event log along with an HTML banner display that will pop up with a success or error message. Only these validated entries are then displayed on the active pacer table, ensuring that outdated pacers or non-existent objects are not executed or displayed.


This design improves system robustness as needed for a production level application by separating configuration from execution which reduces the chances of runtime errors. Once pacers are active, the user is given fine tuned control over execution, with the ability to start of stop individual pacers independently or launch all active pacers simultaneously. All these above features, along with many smaller but equally important improvements to the user experience, were driven by extensive hands-on testing. Backend features could validated using performance testing tools, but frontend functionality required direct, manual interaction to discover bugs and come up with UI optimizations. Approaching the countless hours of system testing from a consumer perspective allowed the application to be developed into a more complete and cohesive package that can be deployed into Barton Hall and other real-world environments.

Lighting Implementation Details

The implementation of the Lighting mode aimed to extend the pacer system into a multimodal wavelight platform, as was the goal to have this be used in Barton Hall. This flexible lighting system would reuse the core architecture developed for the pacer mode while supporting a wide range of visual effect options.

At a high level, the lighting system was implemented using the same software class architecture as the pacer system, consisting of a centralized manager and modular pattern classes. The lighting manager is responsible for owning the LED strip object and polling updates from the active pattern classe, while each individual lighting pattern defines how the LEDs should be updated at each time step and returns this data to the manager.


However, since only a single lighting pattern is active at any given time, the data structures required for lighting were a lot simpler than used in the pacer system. Rather than maintaining a dictionary of multiple active pattern instance, which reduces complexity and inherently prevents race conditions between overlapping patterns.

Despite the structural similarities, several challenges rose during implementation. One major issue involved inconsistent behavior when starting and stopping lighting patterns. Through debugging, it was found that even though each mode (Pacer, Lighting, Music) had its own manager which controlled its own LED strip object, conflicts still occured at the hardware level. This was caused by multiple strip instances attempting to interface and control the same hardware, even if they were not actively driving updates.

To resolve this, the architecture was refactored so that all managers share a single, global LED strip object. This ensures that only one interface to the hardware exists at any time, reducing any funkiness with the software handling of active pacer managers and strip object control.

Another issue was more subtle but involved color ordering. Although the LED strip is labeled as RGBx, it seems to expect color data in GRB order, which was not clearly documented. This mismatch caused green to turn into red and vice versa and required a system-wide adjustment to how color data is formatted for transmission to the strip.

Additional features were also introduced to enhance the lighting mode’s usability and flexibility. These included dynamic lighting patterns, adjustable speed and brightness controls, and consistent integration into the frontend interface. The lighting mode was designed to match the production-level quality of the pacer system, so a lot of thought went into system flow.

For example, mode transitions are handled cleanly, such that the LED strip is automatically cleared and the previous manager is deactivated when switching modes. Within lighting mode, users can switch between patterns without needing to manually stop the current pattern, as the system automatically updates the active pattern instance. Similarly, parameter updates are applied dynamically when new settings are sent to the Raspberry Pi, without requiring a full restart of the pattern.

Additionally, an event log is maintained and displayed to the user as was done in both the pacer and music modes. The buffer and log files are shared between modes so all log messages are saved to a centralized location.

Hardware

The hardware was chosen specifically to meet the requirements of the project while allowing extra room for expansion and versatility. The Raspberry Pi 4 is a suitable microprocessor which allows for GPIO expansion and ease of user interface. Its processor is powerful enough to support a frontend web interface using Flask while also interfacing with hardware like the LED strip and USB microphone. This microprocessor is preferred over the Raspberry Pi Zero for its ability to handle USB connections directly over the stock hardware and for onboard expansion with a touchscreen LCD and external GPIO cobbler. In fact, the USB ports proved useful for last-minute expansion with the USB microphone, which was chosen over the initial analog microphone + ADC combo. The piTFT LCD was also helpful in displaying the IP address of the Pi for web interface connection and could prove useful in future as a minimal user interface for controlling the program (see Future Work section).

Initially, we went with the 12V LED strip which uses the WS2814 chip to drive the LEDs. We preferred the 12V strip as we believed that a higher voltage strip would result in greater signal integrity and brightness uniformity over long distances. However, we ran into many issues when using the rpi_ws281x python library to communicate with the strip. Our initial experiments with the LED strip seemed to show functional behavior under a 3.3V data line, although the LEDs would flicker quite a bit, as seen in the video below.

We then predicted that the strip would likely perform better when driven with a 5V data line. Initially, a 3.3-5V level shifter was proposed to ensure signal integrity with the 5V data line that is expected of the chips on the LED strip. However, we believed that the level shifter was faulty and would only drive the signal needed for the WS2814 12V LED strip under the correct conditions. That is, when level shifted using the 5V reference from the Raspberry Pi, the LED strip seemed to function. However, when level shifted using the 5V reference from the power supply, the LED strip would not turn on at all. We tried linking the negative terminals of both 5V references of the power supply and the Raspberry Pi together, but this did not help.

While performing a test to see if all the LEDs on the strip would turn on using strandtest.py, we were met with faulty results. The signal seemed to travel all the way to the last LED when tested with an oscilloscope, but the LEDs would not turn on, despite putting a high number of LEDs in the test program. By simply tinkering with the LED strip, the LEDs would travel farther, but then the LEDs would freeze and render control useless. Thus, we were skeptical about the integrity of the strip as delicate touches would destroy control. In fact, it was not until later on that we realized that the library probably does not support the WS2814 chip, as there was no constant in the top-level of the library which referred to the WS2814 chip. Only WS2811, SK6812, and WS2812 constants were available.

Thus, we resorted to using the 5V LED strip which uses the SK6812 chip instead. This seems to be a chip that is officially supported by the LED driver library as mentioned earlier. As seen in the video below, the test program runs much more seamlessly on the strip and does not have any glitches in lighting.

In addition, the 5V LED strip better serves the project requirements as it is waterproof, though not initially part of our design proposal. This would be a suitable design for outdoor track spaces as the strip would be resistant to rainy weather conditions and allow for runners to practice in wetter conditions.

Recalling the issues experienced with the level shifter, we decided to analyze the signal with an oscilloscope to ensure that the signal is being translated from 3.3V to 5V properly. When shifting to 5V, however, we find that the flatline of the raw 3.3V PWM signal is not maintained when shifted to 5V. In fact, the signal seems to have a high rising edge, falls back down to near 3.3V, and then slopes upward to near 5V at the falling edge of the signal. This is questionable for integrity of communication from the Pi to the LED chip, especially with the strict timing protocol required of the SK6812 chip. That is,

VIH = 0.7 · VDD

according to the datasheet. That means the input signal must be at least 3.5V. A 3.3V signal is thus below the guaranteed threshold. However, the LED seemed to work fine and no noticeable LED rendering issues could be seen physically, even though the level-shifted control signal was not being generated correctly.
